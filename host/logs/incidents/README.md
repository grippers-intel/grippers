# 사건 기록 로그

`host/logs/`는 `.gitignore`로 통째로 제외돼 있어(미션 로그가 매 실행마다
쌓이므로) 평소엔 커밋되지 않는다. 이 디렉터리는 그 규칙의 예외로, 나중에
다시 찾아볼 가치가 있는 특정 사건의 로그만 골라 `git add -f`로 강제
추가해 보존한다.

## 2026-09-05 밤 — 차량 무반응 사건

- **`mission_20260905_235141.{log,jsonl}`** — APPROACH_PIECE에서
  `cmd=yaw-`를 12초 넘게 계속 보냈는데 로봇 좌표(0.833, 0.392, 91°)가
  전혀 안 바뀌었다. 사용자 코멘트: "왜 안움직여". Pi bringup 로그를
  대조해 보니 `mission_orchestrator`가 `base.apply_velocity(0.0, 0.0,
  -0.25)`와 `rotate_burst`를 정상 주기로 계속 호출하고 있었고 에러·경고가
  전혀 없었다 — Host→Pi→ROS2 명령 전달 경로는 정상이었는데 실제 바퀴만
  무반응이었다는 뜻이다. `dmesg`에도 USB(모터보드 `/dev/rrc`) 이상 없음.
  같은 날 낮부터 진행한 servo1 한계각/GridPathPlanner 변경과는 연결점이
  없다고 판단했다(둘 다 팔 회전각·경로 재계산 쪽이지 베이스 구동 경로가
  아니다).
- **`mission_20260905_235716.{log,jsonl}`** — 위 증상 확인 직후
  `stop_bringup.sh`/`bringup_now.sh`로 Pi 전체를 재기동한 뒤 재시도한
  기록. `[4.9s] cmd=go pose=(...,62.3°)`로 정상적으로 회전을 마치고
  전진으로 넘어가 — 재기동으로 회복됐다.

원인 자체(왜 바퀴가 무반응이었는지)는 로그만으로는 확정할 수 없었다 —
소프트웨어 쪽 증거는 전부 정상이었으므로 배터리·기구적 걸림·STM32 전원
쪽을 의심해야 한다는 게 그 시점의 결론이었다. 이후 재기동으로 실제 회복이
확인됐다는 사실 자체가 이 사건의 유일한 확정 정보라, 재발 시 비교할 수
있게 원본 로그를 그대로 남겨 둔다.
