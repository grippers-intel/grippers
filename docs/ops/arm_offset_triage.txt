작성 2026-09-05 (실기 진단 기록)

셋 다 "EEPROM 이 틀어졌다"처럼 보이지만 원인도 처방도 다르다. 엉뚱한 것을
고치면 시간만 쓰고, ②를 ①로 착각해서 정렬을 걸면 잠긴 관절을 밀어 버린다.


--------------------------------------------------------------------------------
한눈에 보기
--------------------------------------------------------------------------------

  ① Homing_Offset 이 틀어짐  (진짜 EEPROM)
     증상   raw 값의 뜻이 바뀐다 -> 팔이 엉뚱한 자세로 간다
     확인   python3 tools/arm/restore_taught_offsets.py        (읽기 전용)
     처방   python3 tools/arm/restore_taught_offsets.py --apply --yes

  ② 자세가 크래들에서 벗어남  (EEPROM 아님)
     증상   기동 로그  "ERROR: s5 offset +1022 exceeds 800"
     확인   위 숫자는 present - IDLE_CRADLE_RAW 다. 레지스터가 아니라 자세다
            (문턱: WARN 120, ERROR 800)
     처방   python3 tools/align_to_idle.py     <- 단, 아래 경고를 먼저 읽을 것

  ③ 죽은 시리얼 핸들
     증상   서보 6개가 전부 offline
     확인   ls -l /dev/soarm   과  arm_driver 가 연 fd 를 대조
     처방   arm_driver 재시작 (bringup 재기동)


--------------------------------------------------------------------------------
① Homing_Offset — 언제 틀어지나
--------------------------------------------------------------------------------

LeRobot 캘리브레이션이 이 레지스터를 덮어쓴다. 그래서 팀원이 LeRobot 으로
데이터 수집이나 캘리브레이션을 돌리면 그때 틀어진다. restore_taught_offsets.py
가 존재하는 이유가 이것이다.

기준값은 floor_grasp_profiles.TAUGHT_HOMING_OFFSETS 하나다. 교시 자세와 그
자세를 잰 오프셋은 한 쌍이라 같은 파일에 있다.

읽기 전용 실행은 공짜이고 안전하다 — 토크를 건드리지 않는다. --apply 를 줘도
이미 교시값이면 아무것도 쓰지 않는다.

    docker exec IntelPi bash -lc \
      "cd /grippers && python3 tools/arm/restore_taught_offsets.py"

    "교시 당시 캘리브레이션과 일치합니다"  -> ①은 아니다. ②③을 보라
    어긋난 서보가 나오면                   -> 팔 아래 비우고 --apply --yes

  ⚠️ --apply 는 토크를 끈다. 팔이 중력으로 내려온다. EEPROM 쓰기는 토크가
     꺼져 있어야 하고 우회할 수 없다. 팔 아래를 비우고, 물건을 들고 있지
     않은 상태에서 할 것.

  ⚠️ 포트를 arm_driver 가 잡고 있으면 열리지 않는다. 먼저 내릴 것.


--------------------------------------------------------------------------------
② 자세 편차 — 정렬을 걸기 전에 확인할 것
--------------------------------------------------------------------------------

arm_driver_node 가 내는 이 로그는 레지스터가 아니라 자세를 말한다.

    offsets[servo_id] = present - IDLE_CRADLE_RAW[...]      # arm_driver_node

즉 "지금 자세가 등록된 크래들 자세에서 몇 틱 벗어나 있는가"다. EEPROM 과
무관하므로 restore_taught_offsets.py 로는 안 풀린다.

  ⚠️ 자동 정렬을 그냥 걸면 안 되는 경우가 있다. IDLE_CRADLE_RAW 가 실제 교시
     자세와 어긋나 있으면 정렬이 그 차이만큼 관절을 민다. 2026-09-05 에
     wrist_roll(s5)이 909틱 밀린 사고가 그것이었고, s5 는 쓰지 않아서 잠가 둔
     축이다. IDLE_CRADLE_RAW 는 2026-08-20 값인데 팀원이 08-24 에 재교시했다.

  끄는 법 (2026-09-05 배선 추가, 커밋 5d7bab4):

      ros2 launch grippers_bringup bringup.launch.py ... \
        auto_align_on_first_move:=false

  기동 로그에서 확인:

      arm_driver_node ready — auto_align_on_first_move=False

  VLA 파지만 쓸 거라면 꺼 두는 쪽이 안전하다 (다음 절 참고).


--------------------------------------------------------------------------------
③ 서보 6개가 전부 offline 이면 서보가 아니라 포트다
--------------------------------------------------------------------------------

USB 를 다시 꽂거나 전원을 껐다 켜면 ttyACM 번호가 바뀐다. udev 심볼릭 링크는
새 번호를 따라가지만, 이미 떠 있는 arm_driver 는 사라진 장치의 핸들을 계속
붙들고 있다.

2026-09-05 실측 예:

    arm_driver 가 연 포트    /dev/ttyACM2 (deleted)     <- 죽은 핸들
    현재 /dev/soarm         -> ttyACM0                  <- 재열거됨

  확인 방법

      ls -l /dev/soarm /dev/rrc /dev/ttyACM*

      docker exec IntelPi bash -lc '
      for p in /proc/[0-9]*; do
        for fd in $p/fd/*; do
          t=$(readlink $fd 2>/dev/null)
          case "$t" in *ttyACM*) echo "$t  $(tr -d "\0" < $p/cmdline)";; esac
        done 2>/dev/null
      done | sort -u'

  "(deleted)" 가 붙어 있으면 그것이다. arm_driver 를 다시 띄우면 해결된다.


--------------------------------------------------------------------------------
VLA 파지는 ① 에 영향을 받지 않는다
--------------------------------------------------------------------------------

arm_driver_node._load_policy_calibration() 이 매번 live 오프셋을 읽어 delta 를
계산한다.

    live = self._read_with_retry(backend.drv.get_homing_offset, servo_id)
    "delta": int(entry["homing_offset"]) - int(live)

기준을 코드 상수가 아니라 서보 레지스터 실측값으로 잡기 때문에, 오프셋이
틀어져도 그만큼 자동으로 따라 붙는다. EEPROM 을 고정할 필요가 없는 것이 이
설계의 요점이다 — 팔이 공용이라 팀원이 언제든 재교시할 수 있다.

영향을 받는 것은 classic 경로와 교시 자세다(IDLE_CRADLE_RAW, 바닥 파지
프로파일). 그 raw 숫자들이 TAUGHT 좌표계로 적혀 있어서, 오프셋이 바뀌면 같은
숫자가 다른 물리 자세를 가리킨다.

  ⚠️ 어느 경우든 오프셋이 바뀐 뒤에는 arm_driver 를 다시 띄워야 한다.
     delta 표는 노드가 뜰 때 한 번만 계산된다(__init__). 재시작하지 않으면
     낡은 값으로 계산한다 — "EEPROM 이 또 틀어졌다"고 느껴지는 상황의 상당수가
     사실은 값이 아니라 읽은 시점이 낡은 것이다.


--------------------------------------------------------------------------------
평소 습관
--------------------------------------------------------------------------------

  1. 팀원이 팔을 만진 뒤에는 읽기 전용으로 한 번 돌린다 (공짜, 안전)

         python3 tools/arm/restore_taught_offsets.py

  2. 서보가 전부 offline 이면 서보를 의심하기 전에 ttyACM 번호를 본다

  3. 기동 로그의 "offset ... exceeds" 는 EEPROM 이 아니라 자세다

  4. 오프셋을 바꿨으면 arm_driver 를 반드시 재시작한다
